UJI KONSEP

Kenapa vault harus dipisah?

  • Jika database aplikasi bocor, penyerang hanya melihat token, bukan langsung data asli.
  • Vault menjadi komponen sensitif yang perlu perlindungan ekstra.
  • Akses pemetaan token harus dibatasi berdasarkan peran dan kebutuhan.
  • Aktivitas lookup perlu dicatat dan dipantau.
Penting: tokenisasi bukan enkripsi. Token tidak dihitung kembali dari data asli; pemetaan disimpan di vault.
CONTOH IMPLEMENTASI · ALUR END-TO-END

Bagaimana tokenisasi diterapkan pada aplikasi?

1. Input ke layanan tokenisasi

Aplikasi mengirim data fiktif melalui layanan yang berwenang.

2. Simpan pemetaan di vault

Vault membuat token acak dan menyimpan relasi token–nilai asli.

3. Aplikasi memakai token

Database aplikasi menyimpan token, bukan nilai asli.

Contoh data setelah proses

Data asli (misalnya NIM) → Token Vault: token + NIM asli. Aplikasi Kampus: token + data layanan non-sensitif yang diperlukan.

Jika suatu proses benar-benar membutuhkan nilai asli, layanan harus meminta detokenisasi melalui pemeriksaan identitas, otorisasi, alasan akses, dan pencatatan audit.

Tokenisasi berbeda dari hashing: token acak dapat dipetakan kembali melalui vault; hash pada umumnya tidak menyediakan mekanisme pemulihan nilai asli.
Catatan praktikum: database ini adalah simulasi di browser menggunakan penyimpanan lokal (localStorage), bukan server database sungguhan. Jangan masukkan data pribadi nyata. Sistem produksi harus memakai database terpisah, enkripsi, kontrol akses, autentikasi, backup, dan audit log.

UJI PEMAHAMAN

Persetujuan yang Sah

Consent tidak boleh berupa kotak yang sudah dicentang sebelumnya (*pre-ticked boxes*). Harus berupa tindakan afirmatif yang jelas (*clear affirmative act*).

Prinsip penting

Persetujuan harus spesifik, diinformasikan, diberikan secara sah, dan dapat dibuktikan. Tidak semua pemrosesan data harus selalu menggunakan persetujuan; dasar pemrosesan perlu dinilai sesuai konteks dan UU PDP.
